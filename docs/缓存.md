# Honoki 分层缓存与强制失效 (Tiered Cache & SWR)

本文档介绍本项目的**分层缓存架构**、**SWR (Stale-While-Revalidate) 机制**、三大平台响应头适配,以及**强制缓存失效 (Cache Purge)** 的配置与使用方法。

> **重要前提(2026-10 修订)**:Cloudflare 部署时,Worker 生成的 HTML/JSON/RSS 默认属于 `DYNAMIC`,**不会**进入边缘缓存。要让 SSR 页面真正被边缘缓存,必须在 `wrangler.jsonc` 中启用 Workers Cache:
> ```jsonc
> "cache": { "enabled": true }
> ```
> 启用后每个 HTTP 请求都会先查边缘缓存,是否缓存及缓存多久完全由 Worker 输出的 `Cache-Control`(及 `Cloudflare-CDN-Cache-Control`)决定。此字段要求 Wrangler ≥ 4.69.0,与 `compatibility_date` 无关。
> **注意**:`public/_headers` 只作用于**静态资源响应**,对 Worker 生成的响应无效;因此 Worker 页面的边缘 TTL 只能通过响应头表达,不能写进 `_headers`。

## 1. 为什么需要分层缓存?

在基于 Serverless / Edge Function 与 GitHub 内容解耦的博客系统中,常常面临两个核心矛盾:
1. **GitHub API 频率限制(Rate Limit)**:未授权访问每小时仅 60 次,即使带 Token 也仅 5000 次/小时。若无强缓存,多读者并发或频繁冷启动会瞬间击穿限额。
2. **边缘冷启动与延迟**:Serverless 容器在无请求数分钟后会被平台冻结销毁,新访客访问时需要重新执行函数与动态抓取。

本项目通过**多层缓存 + SWR** 缓解这一难题:**开启 Workers Cache 后,绝大多数读者请求由全球边缘节点直接返回已编译好的 HTML,只有内容真正变更时才由主动 Purge 触发回源**,从而大幅降低 GitHub 请求量与首字节延迟。

> 说明:本文档不承诺固定的命中率或延迟数字,实际效果取决于是否启用 Workers Cache、边缘 TTL 配置与访问分布。

## 2. 分层缓存架构

```
                  访客访问
                     │
                     ▼
┌────────────────────────────────────────────────────────┐
│ 第一层:客户端浏览器 (Browser)                             │ ── Cache-Control: public, max-age=0 (每次使用前回边缘校验)
└────────────────────────────────────────────────────────┘
                     │
                     ▼
┌────────────────────────────────────────────────────────┐
│ 第二层:边缘 CDN (Cloudflare / Netlify / Vercel)          │ ── 平台专属头承载差异化 TTL (聚合页 30m / 详情页 24h / 静态 1y)
│  * Cloudflare 需在 wrangler.jsonc 启用 cache.enabled     │
└────────────────────────────────────────────────────────┘
                     │ CDN 未命中 / 后台 SWR 静默预取
                     ▼
┌────────────────────────────────────────────────────────┐
│ 第三层:服务层持久化存储 (Cloudflare KV / Unstorage)      │ ── CACHE_TTL=86400 (24h 常驻,无需每次调 GitHub)
└────────────────────────────────────────────────────────┘
                     │ KV 过期或主动 Purge 强制清空
                     ▼
┌────────────────────────────────────────────────────────┐
│ 第四层:GitHub Raw / REST API 源数据                     │ ── 仅在内容变更且 Purge 后回源
└────────────────────────────────────────────────────────┘
```

### 各层职责分工:

| 层级 | 缓存位置 | 缓存策略 | 作用与体验 |
| :--- | :--- | :--- | :--- |
| **第一层:浏览器端** | 读者本地设备 | `Cache-Control: public, max-age=0` | `max-age=0` 表示「每次使用前都必须回边缘校验」。一旦博主更新文章并清空边缘缓存,**读者刷新后立刻看到最新内容,不会被本地磁盘死缓存卡住**。 |
| **第二层:边缘 CDN** | 全球边缘节点 | **聚合列表页**:边缘 TTL 1800s (30m) + SWR 86400s (24h)<br>**文章详情页**:边缘 TTL 86400s (24h) + SWR 604800s (7d)<br>**静态图片**:边缘 TTL 31536000s (1y) | **分级 TTL 精准平衡时效与性能**:聚合列表与归档页(`/`, `/archive`, `/links`, `/about`)保持 30 分钟强缓存与 24h SWR,文章详情页保持 24 小时强缓存与 7 天 SWR。边缘 TTL 通过平台专属头表达(见第 3 节)。 |
| **第三层:数据存储层**| Worker KV / 内存 | `CACHE_TTL=86400`(24 小时) | 底层清单与文章数据常驻边缘 KV。即使 CDN 未命中穿透,后端函数也直接从 KV 读数据,依然不打扰 GitHub。 |
| **第四层:源数据源** | GitHub 仓库 | 源头 Markdown / JSON | 仅在初次构建或触发主动 Purge 时回源。GitHub Raw 请求**不再附加时间戳**,以复用其自身 CDN 缓存、降低冷启动延迟;内容更新由 KV / 边缘 Purge 负责。 |

## 3. 三大云平台边缘控制头适配

代码在 [`src/utils/cache.ts`](../src/utils/cache.ts) 中通过 `setTieredCache(c, { browserMaxAge, edgeMaxAge, swrMaxAge, tags })` 对全站页面路由及 API 接口注入针对三大云平台的专用指令,并对**聚合页与文章详情页实施分级差异化 TTL**。

**统一约束**:边缘 TTL 与 SWR 一律用 `max-age` 表达。`s-maxage` / `must-revalidate` / `proxy-revalidate` 三者中任意一个出现都会**禁用 `stale-while-revalidate`**(RFC 9111 §4.2.4),因此这些指令不再输出。

* **Cloudflare (Workers / Pages)**:
  - 浏览器层:`Cache-Control: public, max-age=0`
  - 边缘层:注入高优先级的 `Cloudflare-CDN-Cache-Control` 与 `CDN-Cache-Control`:
    - **聚合列表页** (`/`, `/archive`, `/links`, `/about`):
      ```http
      Cloudflare-CDN-Cache-Control: public, max-age=1800, stale-while-revalidate=86400
      CDN-Cache-Control: public, max-age=1800, stale-while-revalidate=86400
      ```
    - **文章详情页** (`/posts/:slug`):
      ```http
      Cloudflare-CDN-Cache-Control: public, max-age=86400, stale-while-revalidate=604800
      CDN-Cache-Control: public, max-age=86400, stale-while-revalidate=604800
      ```
  - 同时输出 `Cache-Tag: <tag1>,<tag2>`,供 `ctx.cache.purge({ tags })` 精准失效(见 3.3)。标签仅保留可打印 ASCII(0x21–0x7E)且长度 ≤1024 的项,CF 消费后该头不会下发客户端。
* **Netlify (Edge Functions)**:
  - 注入专用指令与细粒度标签(伞状标签 `page`/`post`/`api` 供全量清理,具体标签 `home`/`archive`/`post-<title>` 供常规精准清理):
    ```http
    Netlify-CDN-Cache-Control: public, max-age=1800, stale-while-revalidate=86400
    Netlify-Cache-Tag: page,post,post-文章名
    ```
* **Vercel (Edge Runtime)**:
  - 注入标准 CDN 头与标签:
    ```http
    CDN-Cache-Control: public, max-age=1800, stale-while-revalidate=86400
    Vercel-Cache-Tag: page,post,post-文章名
    ```
* **404 与敏感操作接口**:
  - 动态接口、管理端点及文章不存在页面设置 `no-cache, no-store`(见 `setNoCache`),严防错误状态被意外缓存。
  - `/api/*` 另有一层默认中间件:若某接口未自行设置 `Cache-Control`,统一补 `no-store`,避免 Workers Cache 对无缓存头的响应做启发式缓存。

### 3.1 静态媒体与站点图标长效缓存 (Images & Icons)

背景图(`home-bg.webp`)、站长头像(`avatar.webp`)、文章插图及站点图标(`favicon.ico`、`favicon.svg`、`*.png`)属于极低频变更的媒体资产。项目在 `public/_headers`、`src/index.ts`、`vercel.json` 中配置了跨平台长效强缓存。注意 **`_headers` 只影响静态资源响应**,Worker 生成页面不受其约束。

| 资源类型 | 匹配路径 | 浏览器本地 TTL | 边缘 CDN TTL | SWR | 效果 |
| :--- | :--- | :---: | :---: | :---: | :--- |
| **媒体图片** | `/images/*` | 30 天 (`max-age=2592000`) | 1 年 (`max-age=31536000`) | 7 天 | 读者二次访问本地磁盘直出 (`200 from disk cache`),边缘节点常驻 `HIT` |
| **站点图标** | `/favicon*`、`/apple-touch-icon.png`、`/web-app-manifest-*.png` | 30 天 (`max-age=2592000`) | 1 年 (`max-age=31536000`) | 1 天 | 杜绝刷新时的多余 304/REVALIDATED 协商消耗 |

`_headers` 中的边缘 TTL 使用 `Cloudflare-CDN-Cache-Control` 表达(优先级最高且下发客户端前被剥离)。各路径规则必须互不重叠,否则同一资源会命中多条规则,产生重复头或非法值。

### 3.2 缓存键与查询参数 (Query String) 隔离

1. **Wrangler 配置机制**:
   Cloudflare Workers Cache 由 `wrangler.jsonc` 的 `cache.enabled: true` 启用(Wrangler ≥ 4.69.0)。启用后缓存是否生效、TTL 多长由 Worker 输出的 `Cache-Control` / `Cloudflare-CDN-Cache-Control` 决定。**注意**:`s-maxage`、`must-revalidate`、`proxy-revalidate` 会禁用 SWR,故本项目一律用 `max-age` 表达边缘 TTL。
2. **缓存键包含 Path 与 Query String**:
   Workers Cache 的默认缓存键为 **请求路径 + 查询字符串**(不含 host),仅缓存 `GET`/`HEAD`。本博客支持分页(`/?page=2`)和分类筛选(`/?category=xxx`、`/?tag=xxx`),查询参数天然参与缓存键,**不同筛选条件不会串页**。
   > 若在 Cloudflare 控制台额外配置 Cache Rules,**切勿开启「忽略查询字符串 (Ignore query string)」**,否则将导致不同筛选条件共用同一缓存副本,造成串页。
3. **真实浏览器 GET 缓存验证方法**:
   使用 `curl -I` 发送的是 HEAD 请求。建议使用以下命令验证真实 GET 缓存行为:
   ```powershell
   curl.exe -sS -D - -o NUL "https://blog.example.com/"
   curl.exe -sS -D - -o NUL "https://blog.example.com/"
   ```
   第二次请求若返回 `cf-cache-status: HIT` 且 `Age` 逐步增长,即说明边缘缓存正常。
   > 本地 `wrangler dev --local` 不模拟 Cloudflare Workers Cache 网络层,因此本地**不会**出现 `cf-cache-status`,属预期现象;需在真实部署上验证。

### 3.3 各平台缓存清除能力与 Cache-Tag 差异规范

`setTieredCache(c, { tags })` 与 `purgePlatformCaches(env, { urls, tags })`、`purgeWorkersCache(c, { tags, purgeEverything })` 提供统一的调用签名,但三大云厂商底层的清除机制存在能力差异。后端 `/api/posts/purge` 与工作流 `sync-posts.yml` 会同时构造 `urls` 与 `tags`:

| 平台 | 是否输出 `Cache-Tag` 响应头 | 常规更新清理策略 | 手动全刷策略 (`action_type: cdn`) | 架构设计原因 |
| :--- | :---: | :--- | :--- | :--- |
| **Cloudflare Workers Cache** | ✅ `Cache-Tag` | **按标签精准失效**(`ctx.cache.purge({ tags })`) | `ctx.cache.purge({ purgeEverything: true })` | Workers Cache 支持按 `Cache-Tag` 失效(与套餐无关)。**zone 级 `purge_cache` API 对 Workers Cache 无效**,必须用 `ctx.cache.purge()`。 |
| **Cloudflare zone 级 CDN** | — | **精准单文件 URL 列表清除**(`files`: 聚合页 + 最新变动文章,≤30 个 URL),保护 `/images/*` 静态图片 | 全站清除 (`purge_everything: true`) | zone 级 purge 只影响 zone 缓存(如静态资源),与 Workers Cache 是两层。 |
| **Netlify** | ✅ `Netlify-Cache-Tag` | **按页面/文章标签软清理**(`cache_tags`: 聚合标签 + 最新变动文章标签) | 全站清除(仅传 `site_id`) | Netlify 原生免费支持 `cache_tags` 失效,静态图片不含动态标签故天然受保护 |
| **Vercel** | ✅ `Vercel-Cache-Tag` | **按页面/文章标签软清理**(`dangerously-delete-by-tags`) | 按全标签列表清除 | Vercel Edge Cache 原生支持按 Tag 标记失效 |

> 关键区分:Cloudflare 的 **Workers Cache**(Worker 生成的 SSR 页面)与 **zone 级 CDN 缓存**(静态资源等)是**两层独立缓存**。前者只能用 `ctx.cache.purge()` 清理,后者用 zone 级 `purge_cache` API。本项目的 `/api/posts/purge` 会同时清理两层。

## 4. 强制缓存失效工作流 (Cache Purge)

当博主新增、修改或删除了文章时,更新流程遵循严格的**时序保证**:
1. **删除与刷新 KV 缓存**;
2. **清除受影响的边缘缓存**(Workers Cache 按标签 + 各平台 zone 级 CDN);
3. **主动发起 HTTP GET 请求预热新缓存**。

### 4.1 自动刷新与精准失效 (发布/修改文章)
当你在本地推送 Git 提交,或在 **Pages CMS** 后台修改保存文章(`posts/**`)、修改站点设置(`blog.config.json`)、编辑友链(`friends.json`)或修改关于页(`about.md`)时:
1. 自动触发 GitHub Actions 工作流 [`.github/workflows/sync-posts.yml`](../.github/workflows/sync-posts.yml);
2. 自动更新生成 `posts/manifest.json`;
3. **通知博客后端**:调用 `${BLOG_URL}/api/posts/purge` 清空底层 KV 数据。该端点鉴权采用 **fail-closed**:
   - 未配置任何密钥(`PURGE_SECRET` / `GH_TOKEN` / `PAT_TOKEN` / `GITHUB_TOKEN`)时**直接返回 403**,不会匿名放行;
   - 已配置时,请求头 `X-Purge-Secret` 需与密钥恒定时间比较匹配,否则返回 401;
4. **分层精准清除 (Targeted Purge)**:
   - **Cloudflare Workers Cache**:按 `Cache-Tag` 精准失效(`ctx.cache.purge({ tags })`);
   - **Cloudflare zone 级 CDN**:精准清除受影响的核心聚合与订阅页(`/`, `/archive`, `/links`, `/about`, `/sitemap.xml`, `/rss.xml`, `/atom.xml`)及最新修改的文章 URL(在单次 30 URL 限制内);
   - **Netlify / Vercel**:按受影响页面与文章的 `Cache-Tag` 标签软清理;
   - **静态媒体保护**:各平台均避免无差别清空 `/images/*` 静态长效图片缓存;
5. **全链路 GET 自动预热**:工作流末尾自动对全部核心聚合/订阅页(含 `/rss.xml`、`/atom.xml`)及最新文章执行 HTTP GET 访问,让首位读者与订阅器进入时直接命中 `HIT`。

### 4.2 手动一键强刷与缓存管理
在不改动任何代码的情况下,你可以随时手动清除全网所有机房缓存或刷新 KV 缓存:
1. 进入 GitHub 仓库页面 -> 点击 **Actions** 标签页;
2. 在左侧工作流列表中选择 **Sync Posts & Manage Cache**;
3. 点击右侧 **Run workflow** 按钮,在下拉框中选择操作类型:
   - **`all` (全部执行)**:更新文章清单 + 刷新后端 KV 缓存 + 分层精准清除(Workers Cache 按标签、Cloudflare 按受影响 URL、Netlify/Vercel 按页面标签)+ GET 预热;
   - **`kv` (清除 KV 缓存并重新拉取)**:更新清单 + 提交 git + 通知后端重新加载文章与配置;
   - **`cdn` (清除 CDN 缓存)**:调用各平台 API 强制全量清空边缘缓存(Workers Cache `purgeEverything` / Cloudflare zone `purge_everything` / Netlify 全站 `site_id` / Vercel 全标签)。
4. 点击运行即可一键完成!

### 4.3 Pages CMS 后台动作联动
在 Pages CMS 后台的「文章」、「站点设置」或「友情链接」页面中,预置了 **「刷新缓存」** 动作按钮,并在仓库全局动作中提供了 **「同步文章与缓存管理」**,支持下拉选择操作类型,点击后将直接通知工作流执行全链路同步与刷新。

## 5. 环境变量与凭证配置指南

### 5.1 配置总览表格

配置路径:GitHub 仓库 -> **Settings** -> **Secrets and variables** -> **Actions**

| 变量名称 | 所属平台 | 建议存放位置 | 必填/可选 | 说明与获取方式 |
| :--- | :---: | :---: | :--- | :--- |
| **`BLOG_URL`** | **通用** | Variables 或 Secrets | **必填** | 博客在线访问地址 (如 `https://blog.example.com`),用于通知后端清空 KV/数据缓存,并用于 RSS/sitemap/robots 生成绝对 URL。缺协议时可自动补 `https://`。 |
| **`PURGE_SECRET`** | **通用** | Secrets | **推荐** | 缓存刷新鉴权密钥。**建议显式配置**:未配置时端点 fail-closed 返回 403(仅兼容 `GH_TOKEN` / `PAT_TOKEN` / `GITHUB_TOKEN` 作为回退)。 |
| **`CLOUDFLARE_ZONE_ID`** | **Cloudflare** | Secrets 或 Variables | 可选 | 域名 Zone ID(Cloudflare 域名控制台概述页右侧复制),用于 zone 级静态资源清除 |
| **`CLOUDFLARE_API_TOKEN`** | **Cloudflare** | Secrets | 部署必填 / 强刷复用 | **部署时使用的 `CLOUDFLARE_API_TOKEN` 直接复用**(创建时**必须追加** `Zone - Cache Purge - Purge` 权限) |
| **`NETLIFY_SITE_ID`** | **Netlify** | Secrets 或 Variables | 可选 | 目标项目 ID(Netlify 对应项目 -> **Project configuration** -> 复制顶部 **Project ID**) |
| **`NETLIFY_API_KEY`** | **Netlify** | Secrets | 部署必填 / 强刷复用 | **部署时创建的 PAT 密钥直接复用**(变量名 `NETLIFY_API_KEY` 或 `NETLIFY_AUTH_TOKEN`) |
| **`VERCEL_TOKEN`** | **Vercel** | Secrets | 部署必填 / 强刷复用 | **部署时配置过的 `VERCEL_TOKEN` 直接复用**,通过官方 Edge Cache REST API 刷新 |
| **`VERCEL_PROJECT_ID`** | **Vercel** | Secrets 或 Variables | 可选 | **部署时配置过的 `VERCEL_PROJECT_ID` 直接复用**,无需在 Vercel 绑定 Git 仓库 |
| **`VERCEL_ORG_ID`** | **Vercel** | Secrets 或 Variables | 可选 | 若项目部署在 Vercel 团队下填写 Team ID(个人账号留空即可) |
| **`CACHE_TTL`** | **通用** | Variables | 可选 | 底层存储/KV 默认缓存秒数 (默认 `86400` 即 24 小时) |

### 5.2 平台凭证获取与权限精简指南

#### ⚡ 1. Cloudflare:一币两用,创建 Token 时必须追加 Cache Purge 权限
在部署 Cloudflare Worker 时,本来就需要创建 `CLOUDFLARE_API_TOKEN`:
* 在 Cloudflare 控制台创建 Token 时,基于 **Edit Cloudflare Workers** 模板;
* 在权限列表(Permissions)中**必须点击 Add more 追加一项**:
  * **`Zone`** -> **`Cache Purge`** -> **`Purge`**
* 在 Zone Resources 区域选择 `Include` -> `All zones`(或选定你博客绑定的域名);
* ⚠️ **必须追加的原因**:发布文章时自动刷新或手动一键强刷 zone 级 CDN 缓存时,GitHub Actions 将直接调用 Cloudflare 官方 Cache Purge API。**若未在此 Token 中添加 Purge 权限,强刷操作将失败并返回 403 Forbidden**。
* 说明:此处 Token 用于 **zone 级** CDN 清除。**Workers Cache** 的失效由 Worker 内部的 `ctx.cache.purge()` 完成,不需要该 API 权限。

#### 🌐 2. Netlify:无缝复用部署用 PAT
* **`NETLIFY_SITE_ID`**:在 Netlify 对应项目页面,点击左侧菜单 **Project configuration**,在顶部直接复制 **Project ID**。
* **`NETLIFY_API_KEY`**:若之前已配置部署工作流,直接使用当时的 Personal Access Token 即可,两边变量名称完全通用。

#### ▲ 3. Vercel:官方 REST API,彻底解除 GitHub 仓库绑定限制
* 传统的 Vercel Deploy Hook 强制要求在 Vercel 控制台连接 GitHub 仓库,但通过 GitHub Actions CLI 部署的项目在 Vercel 看来是外部上传的,无法创建 Deploy Hook。
* 本项目改用 **Vercel 官方 Edge Cache Invalidation REST API**:
  直接复用部署必须的 **`VERCEL_TOKEN`** 与 **`VERCEL_PROJECT_ID`**,自动按标签标记失效,**无需绑定任何 Git 仓库,无需创建 Deploy Hook**!

### 5.3 部署解耦说明 (无配置零阻断)

1. **部署阶段 100% 独立**:
   多平台部署工作流(`deploy.yml`)只关注编译代码与发布,完全不依赖任何 Cache Purge 变量。
2. **清理工作流安全兜底**:
   在 `sync-posts.yml` 中,针对每个平台的清理都有判空守卫。若你尚未填写某个平台的 ID,Actions **仅会输出一行提示并优雅跳过,状态依然为绿色的成功(Success)**,绝不阻塞流程。
3. **随手补填即可激活**:
   你完全可以先完成博客项目的首次部署,待各平台部署成功分配好 Project ID / Zone ID 后,随时在 GitHub Secrets 中补填,即可无缝激活全网 CDN 强刷能力!
